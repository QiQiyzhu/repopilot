# RepoPilot：把“绿灯”讲成可核验的判断

新增工程案例：[冻结开发 capsule](capsule-evaluation.md)。从一份真实修复扩展到 6 个冻结任务与两种上下文配置时，先解决 oracle 不进入候选执行空间、代码只能在受限 Docker 里运行、调用前记账和未知账单停止。对应代码为 `capsule_eval.py`、`capsule_sandbox.py`；这不意味着已有 held-out 泛化成绩。真实结果以协议链接中的实际 receipt 为准。

这份讲解围绕[实际决策案例](decision-case-study.md)，不是一张新增功能清单。措辞使用 AI-assisted，只有在本人读过源码、重跑过案例并能解释结果后，才采用第一人称。原 A–T 手册保持不变。

## 30 秒：一个问题和一个证据

“RepoPilot 是一个 AI-assisted 开发的 Coding Agent harness。我用它追问：测试全绿，任务就完成了吗？一个距离函数补测案例里，两个方案都通过 93 项回归。水平用例却放过了曼哈顿距离错误，斜向 3–4–5 用例明确报出 7 不等于 5。所以我把进程通过与任务验收分开，用独立可执行契约检查模型没有证明的部分。这是实际控制实验，没有包装成 LLM 成功率。”

## 3 分钟：为什么这样设计

先展示[两行候选与对照表](decision-case-study.md#实际对照)，请面试官判断是否接受两份全绿补测。这里的任务不是修复一个当前错误，而是新增能保护指定行为的回归测试；这一区别决定了验收方式。

接着解释三层证据。完整回归说明新测试在正确实现上可运行，未破坏已有套件；文件与 diff 检查说明改动触达了要求的位置；只有在临时错误实现下单独运行候选，才能知道这份补测是否有辨别力。既有测试即使能发现错误，也不能冒充新测试的贡献。

再讲实现边界。实验复用固定 Git 归档、受限工具路由、现有 verifier 与外部 TypeScript 契约，不需要再造一个 Agent。A 的测试是合理但不足的手写控制，B 是数据集参考控制；没有调用 Fake 或真实模型，因此结果不说明模型会多频繁地犯这种错。

最后讲一次反过来审查评估器的发现：之前任意 `not passed` 都可能被统计成杀死 mutant，实际上超时不是成功。共享判定现在拒绝把超时／信号退出记成控制通过，案例还检查预期的 `7 !== 5`。用真实超时子进程做了回归，保留了下一步盲测评估器的必要性。

## 五个高价值追问

**1. 现有 verifier 两次都通过，是不是说明它没有价值？**

不是。它提供可重复的命令与文件合同检查，能拒绝未改文件、未执行测试等情况。但它不知道没有被编码进验收的语义。“verified”必须带作用域。此案例的任务最终判定来自更强的独立验收，不应把 in-loop 标签当成万能证明。

**2. 你已经公开了 mutation，候选会不会只针对它过拟合？**

会。这是评估机制的已知正负控制，不是泛化测量。真实模型试验应在开始前固定未暴露的变体、预算和失败分类，并保留未改善结果；不能把本例 1／1 接受改写成模型成功率。

**3. 为什么不直接跑全部测试来杀 mutation？**

这里要评估的是“新补测试”的价值。旧测试杀死 mutant 说明仓库已有保护，无法证明候选新增了所要求的保护。两个 scope 都有意义：正确基线跑全回归，mutant 上只跑这份候选。

**4. exit 1 就能说明测试抓到了业务错误吗？**

不能。它至少排除了 timeout／signal 类故障被误算，但 exit 1 还可能有别的原因。本例先要求正确实现通过，再验证已知 mutation 的特定 `7 !== 5`。这个 case-specific oracle 不是面对任意敌对测试的安全判断器；下一步要独立验证更多失败分类。

**5. 为什么不让第二个 LLM 评审，或用更复杂的 Agent 自动修复？**

因为当前不确定性已经能用一个便宜、确定的实验消除。模型可帮助解释或提出候选，但执行证据更适合回答这个精确行为问题。增加代理数量不能补上缺失的验收合同；任意执行能力还会扩大信任边界。

## 可以诚实放进简历的一句话

“AI-assisted 构建并复现 Coding Agent 完成度反例：两份补测均通过 93 项回归，独立 mutation 契约拒绝缺乏辨别力的方案；补充真实进程超时负控制，避免将基础设施失败计为评估成功。”

不要改成“将 LLM 成功率提高到 100%”“防住所有测试污染”或“工业线上 Agent 已落地”。本例没有真实模型运行、客户使用或通用安全保证。

## 补充追问：接上真实模型后，你改变了什么判断？

另一次 [真实 DeepSeek clamp 任务](evidence/deepseek-task.json) 已完成：模型四次调用，自主复现三个失败、提交修改、复测、finish；运行时独立复验三个测试，还检查原测试未被修改。它用的表达式是 `min(high, max(low, value))`，没有拿到 Fake 的预设 patch。此例证明真实模型进入了工具和验收流程，不能替代上面的完成度反例或 36 个任务的系统评估。

值得讲的下一步是预算归因：本次 10,600 个观测 tokens 里，输入占 10,277，约 97%；不能只盯着 323 个输出 tokens。可以预先固定同样任务、相同模型和验收，对失败日志截断与重复上下文压缩做对照，比较 token、额外工具调用、成功及漏诊；先保留可能恶化的结果。这是根据本次记录提出的下一项实验，**还没有做出节省成本或提升准确率的结论**。
